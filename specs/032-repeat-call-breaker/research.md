# Phase 0 Research: Repeat-Call Notice and Ledger Retry Collapse

**Date**: 2026-09-01. Method: four parallel read-only survey agents over the live SymForge index (ledger lifecycle, envelope/outcome surfaces, ledger renderers, index-currency machinery), ~694k tokens, all anchors verified against source at survey time. Line numbers drift; re-verify with `search_symbols`/`get_symbol_context` at implementation time.

No `NEEDS CLARIFICATION` items remained after the survey; each decision below records what was chosen, why, and what was rejected.

## R1 — Detection seam: `SymForgeServer::call_tool`

**Decision**: Implement repeat tracking as post-dispatch processing in `SymForgeServer::call_tool` (`src/protocol/mod.rs:2130-2198`).

**Rationale**: Its own doc comment states stdio and HTTP `/mcp` converge there. Tool name and canonical arguments are readable pre-dispatch (already deserialized at 2142-2155; must be cloned before `ToolCallContext::new` consumes the request at 2157). The full `CallToolResult` is observable and mutable post-dispatch, and three per-call post-processing steps already live at this seam as precedent: the compact-surface gate (2135), central project-evidence `_meta` attachment (2173, single-writer), and error-shape reclassification (2181-2190).

**Alternatives considered**:
- *Per-tool wrappers* (`statused_tool_result`, 25+ call sites in `tools.rs`): rejected — massive churn, and every future tool must remember to opt in (checked, not structural).
- *STEL admission controller* (`evaluate_plan_tuned`): rejected — reachable only from the compact facade (`src/protocol/tools.rs:11243`); the full surface (default) would get nothing.
- *Ledger-derived detection*: rejected on evidence — see R2.

**Known scope hole (accepted, documented)**: raw daemon-IPC callers that hit `execute_tool_call` (`src/daemon.rs:5892`) without an MCP adapter in front bypass `call_tool`. Every MCP-served client (stdio, daemon-backed stdio adapter, HTTP `/mcp`) is covered because the adapter's own `call_tool` wraps the final response.

## R2 — The ledger is NOT the detector (survey finding that reshaped the feature)

`StelLedgerEvent` has exactly one constructor (`build_ledger_event`, `src/stel/ledger.rs:84-135`) and one append site (`finalize_symforge_with_ledger`, `src/protocol/tools.rs:12269-12319`), called only by the two compact-facade STEL handlers (`tools.rs:11295/11527/11744/11823`), which refuse unless `SYMFORGE_SURFACE=compact` (`tools.rs:11018-11024`). **No granular tool ever appends a ledger event**, and the event records no argument identity at all — `finalize_symforge_with_ledger` takes `_request` and never reads it (`tools.rs:12272`); `plan_id` is wall-clock millis + query *length* (`src/stel/planner.rs:1230-1236`), not an identity.

Consequence: US1 detection is serve-path state; the spec assumption was amended 2026-09-01 to match. US2 remains a rendering feature over whatever events exist (compact-facade sessions populate them).

## R3 — Fingerprint: reuse `RequestHash::for_tool_request`

**Decision**: `RequestHash::for_tool_request(tool_name, &canonical_json_args)` (`src/idempotency.rs:42-57`), key = `(tool_name, RequestHash)`.

**Rationale**: Generic (hashes canonical JSON under a domain-separated frame prefix, `src/idempotency.rs:13`), crate-exported (`src/internals.rs:46-47`, `src/lib.rs:24`), and already trusted by four production consumers (`begin_mutation_replay` `src/protocol/edit_tools.rs:644-677`, `index_folder` `tools.rs:8008`, daemon `index_folder_for_session` `src/daemon.rs:1585`, knowledge-curation apply `src/protocol/knowledge_curation.rs:438-440`). Only its `FileReplayStore` persistence half is replay-specific; the hash type is free-standing. Nothing is stripped for read tools (no `idempotency_key` on them).

**Alternatives considered**: a new hash — rejected (duplicate of an existing, tested primitive; §CLAUDE.md "already in this codebase" rule). Semantic argument normalization (defaults filled, fields ordered) — rejected for v1: canonical-JSON equality can only produce false *negatives* (spec Edge Cases explicitly accepts this; a false positive is the only unacceptable direction).

## R4 — Eligibility allow-list (the false-claim firewall)

**Decision (revised by R12)**: `REPEAT_ELIGIBLE_TOOLS`, pinned by a test, membership exactly **5 tools**: `search_symbols`, `search_text`, `get_repo_map`, `find_references`, `find_dependents`.

**Rationale**: eligibility means "the rendered output is fully determined by the published index generation the response's evidence names". The adversarial round proved the original 7-tool list failed its own criterion twice — the per-tool proof this section demands was not actually performed for two members. Both are now excluded (rows one and two below).

**Exclusion table (each exclusion is load-bearing; widening requires a per-tool proof)**:

| Excluded | Why a notice could be false |
|---|---|
| `get_symbol` (R12 refutation) | Repeat serves short-circuit into the session cache-hit advisory body, which embeds wall-clock `session_age_secs` twice (`src/protocol/format.rs:5833-5865`; recomputed per hit, `src/protocol/session.rs:243`), and the `force_refresh` lane appends an elapsed-seconds dedup footer (`src/protocol/tools.rs:4487-4510`). Serves 1/2/3 are three different byte sequences on a fully unchanged index. Its repeats already get a purpose-built "you already have this" advisory — the notice adds nothing there. |
| `search_files` (R12 refutation) | `rank_by="frecency"` reorders hits with `SystemTime::now`-decayed scores from the frecency store (`src/protocol/tools.rs:6650-6710`), which is bumped by interleaved commitment reads that deliberately do NOT reset runs (spec FR-002), and is a cross-process SQLite other symforge processes mutate with no publication anywhere (`src/live_index/frecency.rs`). Ordering can change while evidence stays equal — and those mutations are unobservable from the serve path: a textbook "cannot observe ⇒ cannot claim". |

| Excluded | Why a notice could be false |
|---|---|
| `get_symbol_context`, `get_file_context` | Enrich output with knowledge-store backlinks; knowledge mutations (`curate_knowledge`) are not proven to move the compared evidence generation. Until proven, out. |
| `search_knowledge`, `review_knowledge`, `curate_knowledge`, `explore`, `ask` | Knowledge/heuristic surfaces; same proof gap, plus `ask` routing is not contractually deterministic. |
| `get_file_content` | Can serve raw-disk reads through `admit_disk_read` (`src/protocol/read_gate.rs`) — disk is not fenced by index evidence. (Its repeats already get the session cache-hit body, R7.) |
| `what_changed`, `diff_symbols`, `validate_file_syntax` | Read git working tree / refs / disk — envelope uses `never_collapse` for exactly this reason (`src/protocol/tools.rs:3375-3391`). |
| `status`, `health`, `health_compact`, `context_inventory`, `investigation_suggest`, `conventions` | Time-varying, counter-bearing, or heuristic output. |

| `symforge`, `symforge_retrieve` | Facade/CCR-redemption lanes with their own cache-hit reporting (`format_cache_hit_body`, CCR handles). |

**Alternatives considered**: deny-list (rejected: new tools would default-in — a false-claim risk by default); deriving eligibility from the envelope's collapsed `Trust:` line (rejected: string-shaped coupling, the exact defect class `search_format.rs:3-16` documents repairing).

## R5 — Errors count as serves (single normative rule: data-model.md's state machine)

A serve of an eligible fingerprint with equal observed evidence ADVANCES the run **regardless of outcome class** — `NotFound`, `EmptyResult`, and `InvalidRequest` included (note `OutcomeClass::is_error` is true for `InvalidRequest` and `InternalFailure` only, `src/protocol/result_status.rs:40-42`): the A019 motivating data was precisely agents re-issuing *failing* identical calls. The notice text and `_meta` attach to whatever the third identical serve returns; `isError` is never modified by the notice. Exactly two clearing rules: (1) an **observed** `InternalFailure` clears the run — an internal failure is not evidence the next attempt fails; (2) on lanes where `OutcomeClass` is unobservable (the daemon-proxied plain-String lane carries no `symforge/result_status` `_meta`, only the evidence header — `src/daemon.rs:2508-2534`), a response with `isError == true` clears conservatively. The R12 round found three artifacts stating three different versions of this rule; data-model.md's state machine is now the one normative statement and plan.md/this section defer to it.

## R6 — Grounding: `ProjectEvidence` equality, and the honest wording

**Decision**: a run advances only while the full `ProjectEvidence` value (`src/protocol/result_status.rs:58-68`: project_id, project_name, canonical_root, generation, index_state, load_source, index_files, index_symbols) attached to each response equals the run's stored evidence. Notice construction requires a `RepeatWitness` obtainable only from that observed equality. Evidence absent ⇒ run cleared (cannot observe ⇒ cannot accumulate ⇒ cannot claim).

**Rationale**: evidence is attached centrally per-response (`attach_project_evidence_meta`, `result_status.rs:151-167`, called at `mod.rs:2173`; single-writer). Comparing what the responses actually carried IS the observation — it works identically on the local lane and the daemon-proxied lane (where the header/`_meta` mirrors worker state), and full-struct equality is deliberately stricter than any single counter: any drift (generation, file/symbol counts, index_state, root, load_source) resets the run. The index-currency survey confirmed the underlying counters (`PublicationFence` triple, `src/live_index/store.rs:988-1001`; `content_generation` bumped only on real content change at store.rs:3365-3374) and confirmed the limit that dictates wording: uncommitted disk edits reach the index only through the asynchronous watcher pipeline, so the honest claim is "no index change **published** between these serves", never "the files have not changed". `FreshnessStatus` semantics (`src/domain/index.rs:961-982`) say the same. Additionally the run must observe `index_state` equal AND the evidence generation equal — a content-preserving republish (freshness flip, `swap_and_publish_retaining_content` store.rs:3345-3347) that changes evidence resets the run; conservative and correct, since the *envelope* of a re-served response could legitimately differ then.

**Alternatives considered**: reading `publication_fence()` directly at the seam (rejected for v1: correct on the local lane but unavailable for daemon-proxied granular calls, splitting the design into two mechanisms; evidence equality covers both lanes with one mechanism and is strictly observed — it can be revisited if evidence is ever detached from responses); comparing only `generation` (rejected: full-struct equality is cheaper to reason about and strictly safer).

**Lane caveats (R12 corrections to this section's earlier "works identically on both lanes")**:
- "Evidence absent" does not exist on the wire: `attach_project_evidence_meta` ALWAYS writes the key — real evidence or the `{"bound": false, "reason": "project_evidence_unavailable"}` marker (`src/protocol/result_status.rs:151-167`). The observable condition is "the value does not deserialize as a full `ProjectEvidence`". The tracker holds TYPED evidence only, never raw `_meta` JSON — comparing raw values would let two `bound:false` markers compare equal and accumulate toward a false notice. A full-shaped evidence with the `"unbound"` placeholder `project_id` (`result_status.rs:149-150`) is also treated as unobserved (no project to be current about).
- **Set-valued cross-project calls are a documented dead zone**: when a request carries a `projects` argument, the daemon seeds no evidence and strips the header (`src/daemon.rs:4366-4407, 4567-4571, 4674-4676`) and the adapter clears its seed (`src/protocol/mod.rs:1117-1122`) — every serve on that lane is marker-shaped, so runs never accumulate and the notice never fires there. False negatives only; pinned by a non-emission oracle; recorded in spec Assumptions. Cross-project coverage would need an aggregate evidence receipt first — explicitly out of scope.

## R7 — Relationship to the existing session read cache (revised by R12)

`get_symbol`/`get_file_context`/`get_file_content` repeats already short-circuit through the session cache (`FetchKey{kind,path,symbol,params_hash}`, `src/protocol/session.rs:18-24`, hits at `session.rs:294-320`, advisory body `src/protocol/format.rs:5833-5865`), whose `params_hash` binds project + publication + content generation (`session.rs:63-67, 448-499`) — the cache is *stricter* than content identity. The R12 round refuted the original conclusion that the notice "complements" the cache on `get_symbol`: the cache-hit advisory body is time-varying (`session_age_secs`), so a "cannot differ" claim on top of it would be false, and `get_symbol` is now EXCLUDED (R4). The division of labor is clean instead: the session-cached tools get their purpose-built "you already have this" advisory from the cache; the notice covers the five *uncached* index-determined read tools, which today give a looping agent no repeat feedback at all. `force_refresh=true` produces a different fingerprint (different args), correctly starting a separate run — moot for eligibility now, still true for fingerprint semantics.

## R8 — Notice delivery: text append + `_meta`, threshold 3

**Decision**: at count ≥ `NOTICE_THRESHOLD = 3`: append the notice paragraph to the response's final text content block, and insert `_meta["symforge/repeat_notice"]` (contract in `contracts/repeat-notice.md`, versioned like `RESULT_STATUS_META_KEY` with `contract_version: 1`).

**Rationale**: the notice's purpose is to stop an LLM retry loop, and many harnesses show models only the text content — `_meta`-only would be invisible where it matters most; text-only would be invisible to programmatic clients. Both, or it under-delivers. Appending (never prepending/rewriting) keeps FR-004's byte-stability: original content is a strict prefix. Threshold 3 honors both the spec rationale (first retry after a transient failure is legitimate) and the repo's B5 counter-precedent against always-on tips (`src/protocol/tools.rs:4335-4336` — "tips stay rare + contextual"). A new `ResultStatus` field was rejected: the struct is `Copy` with a frozen two-field contract (`result_status.rs:169-173`); a separate single-writer `_meta` key follows the established FR-319 seam pattern instead.

**CCR note**: token budgets are enforced inside per-tool handlers before the seam (`enforce_token_budget_with_ccr`, `src/protocol/ccr.rs:356-371`), so the appended ~40-token notice can marginally exceed a `max_tokens` cap. Accepted: the notice exists to *end* a loop that is burning far more than 40 tokens per iteration.

## R9 — Tracker state, bounds, and session scoping (revised by R12)

**Decision**: `Mutex<RepeatTracker>` on `SymForgeServer` (beside `stel_ledger`, `src/protocol/mod.rs:255/280`); `HashMap<RepeatKey, RepeatRun>` with a **session discriminator in the key**; `REPEAT_TRACKER_MAX_ENTRIES = 512`, overflow policy `clear()`.

**Rationale**: the original "process-global on HTTP serve — documented, consistent with the session ledger" position was refuted (R12 BLOCKER): `symforge serve` shares ONE `Arc<SymForgeServer>` across every HTTP client (`src/server/serve.rs:488-502`), so an unscoped tracker would let client A's two serves plus client B's one serve fire a "served 3x ... stop retrying" notice at B's FIRST call — a false claim about B's behavior, and a direct violation of spec Scenario 5 (a MUST). Precedent describes the ledger's scope; it does not license contradicting this spec. The fix is structural: the key carries the session identity the seam OBSERVES — process-constant on stdio (one client per process = the session), the rmcp per-session identity on the shared HTTP lane (T001 verifies what `RequestContext` exposes there), and **where no per-session identity is observable on a shared lane, that lane never accumulates** (unattributable counts are unobserved claims; spec FR-002). The unbounded-`Vec` lesson from `SessionLedger` (`src/stel/ledger.rs:16-48`, no eviction) is not repeated: the map is capped, and the overflow policy can only lose true notices (false negatives), never create a false claim. LRU was rejected as unearned complexity at 512 entries (`ponytail:` comment required at the clear site naming the ceiling and the LRU upgrade path).

## R10 — Feature-cell discipline (embed) — CORRECTED by R12 (the original claim was inverted)

`src/protocol/` and `src/stel/` are `#[cfg(feature = "server")]` at the crate root (`src/internals.rs:97-99, 107-109`; `src/lib.rs:53-62`), so under `--no-default-features --features embed` **none of the new US1/US2 code compiles at all** — no seam, no `repeat.rs`, no `collapse_runs`, no status/admin changes. The original R10 asserted the opposite and prescribed embed gymnastics for `repeat.rs`; that obligation was vacuous and is withdrawn. What remains true: `src/stel_core/` IS in the embed cell (`src/internals.rs:75-77`), and this feature touches `src/stel_core/ledger_store.rs` (additive SELECT/`StoredLedgerRecord` widening) — so the embed gate stays in the T019 battery as a regression check for that shared module, and the repo's `#[cfg(all(test, feature = "server"))]` helper discipline still applies to any test helper added in `stel_core` whose consumer is server-side. A green embed cell proves nothing about the server-gated feature code — do not cite it as feature verification.

## R11 — Collapse identity and its consumers (revised by R12: two lanes, not one)

**Decision**: one generic algorithm (`collapse_runs(items, identity_key)`), two lane identities — the in-memory `StelLedgerEvent` lane and the durable `StoredLedgerRecord` lane; full field tables in data-model.md. Event-lane identity = every field EXCEPT `ts_ms`, `plan_id` (both clocks — `plan_id` embeds wall-clock millis, `src/stel/planner.rs:1230-1236`) and the four per-call measurements, compared via a helper that **exhaustively destructures** the struct so a future field breaks compilation and forces an identity decision (Constitution P5). Durable-lane identity = the stored columns with `session_id` included (rows from different sessions never merge), `accepted`/`eligible_h6` deliberately excluded, and `pff_bypass`/`cache_hit`/`degrade_flags_json` **added to `recent()`'s SELECT and `StoredLedgerRecord`** so identity does not silently merge rows differing in them (`equivalence` has no column — documented coarseness). `recent()` returns newest-first (`ORDER BY id DESC`, pinned at `src/stel_core/ledger_store.rs:1101-1113`); the admin lane reverses to chronological before collapsing. Consumers: the status view via new `StelStatusContext.trailing_run` fields computed in `from_server` (the formatter alone cannot see events — `src/stel/status.rs:75-153, 226-240`; proxy overlay reuses the same formatter at 282-291 so worker/proxy cannot drift, and its prefix-match line replacement at `src/protocol/tools.rs:3826` tolerates the suffix) and the new admin `recent_runs` (first production caller of `recent()`).

**Why rendering-only is load-bearing (survey finding)**: multiplicity is a *consumed input* elsewhere — `summarize_calibration` verdicts gate on corpus size (`TUNING_MIN_CORPUS = 24`, `src/stel_core/calibration.rs:333-360`), durable `summary()` is COUNT/SUM SQL (`ledger_store.rs:778-815`), retention pruning is count-based (cap 2000). Collapsing at storage would change calibration verdicts and admin totals — that is why FR-009 pins collapse to presentation, and why FR-008 holds by construction (aggregates are computed from uncollapsed storage).

**Blast-radius pin inventory** (verify each during implementation; reconcile deliberately, never loosen): `tests/stel_status.rs:141,166-168`; `src/stel/status.rs:482,559,576,597` (+ the `sample_context` fixture at 421-434, which the new context field touches); `tests/surface_honesty.rs:268,293,314,340-348,420-442,542-563`; `src/protocol/tools.rs:13146-13167,13272`; `tests/admin_api_v1.rs:160-164,210-214` (its seeded 3 events are identity-identical → collapse ×3; reuse as the FR-008 control); `tests/admin_render.rs:172-186`; `tests/stel_l4_ledger.rs:125-182,241` (additive `StoredLedgerRecord` fields); `tests/stel_ledger_persistence.rs` (row-level SQL pins); `tests/stel_symforge_edit.rs:80-82`; `src/stel/golden_replay.rs:239-240,302-303`; `src/server/admin/api_v1.rs:618-642`; **`scripts/verify-tools.cjs` snapshot fixtures** (R12-found missed consumer: its readiness probe repeats the first `search_symbols` snapshot case's exact query in-session, `verify-tools.cjs:334-352, 465-467` — the probe gets a fingerprint-distinct argument as part of this feature so the notice can never enter a release-gate snapshot). Survey expectation: only seeds producing ≥2 identical consecutive events change rendering; everything else stays byte-stable. Verify, don't assume. Note the R12 spot-check independently confirmed seven of these pins are contains/field-access asserts that survive a suffix annotation and additive serde fields.
